# أوامر التوريد — واجهة Next.js (`supply_web`)

الواجهة التشغيلية لمشروع أوامر التوريد. **أودو هو مصدر الحقيقة الوحيد**: لا تُخزَّن هنا بيانات أوامر أو أصناف.
يخزّن التطبيق فقط مستخدميه وأدواره وصلاحياتهم (SQLite محلي).

## كيف يعمل

```
المتصفح ──► Next.js (الخادم) ──► أودو  /json/2/supply.api/<method>   (مفتاح API في الخادم فقط)
              │                    └─► /supply_api/print/<kind>/<html|pdf|xlsx>/<id>
              └─ SQLite: المستخدمون، الأدوار، سجل التدقيق
```

- **الصلاحيات تُحدَّد هنا.** كل مستخدم له دور، وكل دور مجموعة صلاحيات قابلة للتعديل من *الإعدادات ← الأدوار*. تُفحص في
  الخادم (صفحات + Server Actions + مسار الطباعة)، والواجهة تُخفي ما لا يملكه المستخدم فقط للراحة.
- **أودو لا يعرف إلا حساب التكامل.** الشخص الفعلي يُرسَل في `context.ext_user_id` فيُسجَّل في الأمر وسجل التعديلات
  ("بواسطة أحمد عبر التطبيق"). كل مستخدم تطبيق يُزامَن إلى أودو (`ext_user_sync`) بدور `manager` لأن القرار هنا.
- **كل كتابة لها `idempotency_key`** تُولَّد مرة لكل نية مستخدم؛ الضغط المزدوج أو إعادة المحاولة لا يكرّر الأثر في أودو.
- مفتاح أودو لا يصل للمتصفح أبداً؛ الطباعة والتحميل تمر عبر `/api/print/...` بعد فحص الصلاحية.

## الشاشات

لوحة التحكم · أوامر التوريد (بحث ومرشحات) · أمر جديد · تفاصيل الأمر (مسح باركود، تعديل مع سبب، استبدال، حذف، إضافة صنف،
تجهيز التسليم/الاستلام، فاتورة من الفعلي، أمر بيع/شراء، طباعة/PDF/XLSX، المستندات، سجل التعديلات) · التنبيهات
(الصلاحية، المشتريات التلقائية) · التسوية الجماعية · الخصومات المؤجلة · المستخدمون · الأدوار والصلاحيات · الاتصال بأودو.

## التشغيل

```bash
cp .env.example .env.local     # ثم املأ ODOO_URL و ODOO_API_KEY و SESSION_SECRET
npm install
npm run dev                    # http://localhost:3000  (أول زيارة: إنشاء مدير النظام)
```

ربط أودو: ثبّت `supply_api`، أنشئ مستخدم تكامل (مجموعة *Supply Orders / Manager* + صلاحيات المحاسبة والمخزون)، ولّد له
مفتاح API، واضبط المعامل `supply_order.service_user_id` برقم المستخدم. (التفاصيل في `custom_adons/supply_api/README.md`).

## الاختبارات

```bash
npx playwright test            # 9 سيناريوهات في متصفح Chrome حقيقي
```

تعمل الاختبارات على **أودو تجريبي** (`e2e/mock-odoo.mjs`) بنفس شكل ردود `supply.api` حسب `docs/API_CONTRACT.yaml`،
فلا تحتاج خادم أودو. تغطي: الإعداد الأول، الدخول، إنشاء أمر وتأكيده وتسليمه وفوترته، المسح، التعديل بسبب، الاستبدال،
الطباعة، الأدوار والصلاحيات (وفرضها في الخادم)، التنبيهات، التسوية، الخصومات المؤجلة، منع التكرار. لقطات الشاشة في `e2e/shots`.
الاختبار على أودو الحقيقي خطوة منفصلة (تحتاج مفتاح API).

## نسخة سطح المكتب (لاحقاً)

صُمّم التطبيق ليُغلَّف دون إعادة كتابة: الخادم مستقل (`NEXT_OUTPUT=standalone npm run build` ثم
`node .next/standalone/server.js`)، وبياناته المحلية في `DATA_DIR`، والإعدادات من متغيرات البيئة. غلاف Electron/Tauri
يشغّل هذا الخادم محلياً ويفتح نافذة عليه، ويحفظ `ODOO_URL` والمفتاح في مخزن مفاتيح النظام.

## ملاحظات تقنية

Next.js 16 مع `cacheComponents` معطّلاً عمداً (كل الشاشات حيّة وخاصة بالمستخدم). الاتجاه RTL، الخط Cairo، والأرقام
لاتينية داخل نص عربي (`.num`).
